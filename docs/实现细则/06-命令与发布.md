## 常用命令

```bash
# 日常
npm install
npm run tauri dev        # 桌面应用（需 Rust；Vite 固定端口 1420；WSL 里能跑，libEGL 几行警告正常）
npm run check            # 类型检查（svelte-kit sync + svelte-check；当前 0 errors / 0 warnings）
npm test                 # 前端 + 脚本单测（vitest + jsdom，45 文件 / 834 项）
npm test -- src/lib/typst-engine.test.ts   # 跑单个测试文件
npm run format           # prettier 全量格式化（`format:check` 只查不改）
cargo test --manifest-path src-tauri/Cargo.toml   # Rust 单测（61 passed / 6 ignored；那 6 个是按需跑的探针/夹具）
cargo fmt --manifest-path src-tauri/Cargo.toml             # rustfmt（默认风格；`-- --check` 只查不改）
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings   # 告警即错误（与 CI 同一条）
npm run dev              # 仅前端 UI（无预览/文件功能；非 Tauri 环境显示"请使用桌面应用版本"提示页）
npm run build            # 前端生产构建（输出 build/）
cargo check --manifest-path src-tauri/Cargo.toml   # 只查 Rust 壳（CI 里已被 clippy 取代，本地想快查可以用）
node scripts/check-fonts.mjs                       # 打包字体魔数校验

# 本地打包（配置里已有 pubkey → 缺私钥会直接失败）
TAURI_SIGNING_PRIVATE_KEY_PATH=~/.tauri/typst-pad.key TAURI_SIGNING_PRIVATE_KEY_PASSWORD=… npm run tauri build

# 浏览器验收（无显示器环境的主力验收手段）：**换端口跑，别跟 tauri dev 抢 1420**
npm run dev -- --port 1425
BROWSER_CHECK_PORT=1425 node scripts/browser-check/wysiwyg.mjs          # 290 项交互验收 + 截图
npm run fixtures:math
BROWSER_CHECK_PORT=1425 node scripts/browser-check/wysiwyg-visual.mjs   # 20 项真实排版视觉验收
BROWSER_CHECK_PORT=1425 node scripts/browser-check/probe.mjs            # 页面坏了先用它看

# 写作模式「块级渲染」三套（需 headless Chromium，见「环境备忘」；CDP_PORT 默认 9333）
CDP_PORT=9335 BROWSER_CHECK_PORT=1425 node scripts/browser-check/writing-blocks.mjs         # 桩产物，133 项
npm run fixtures:blocks                                                                    # 导出真实切片 + 点击探针
CDP_PORT=9335 BROWSER_CHECK_PORT=1425 node scripts/browser-check/writing-blocks-visual.mjs  # 几何等价 + 链接热区，76 项
CDP_PORT=9335 BROWSER_CHECK_PORT=1425 node scripts/browser-check/writing-blocks-hit.mjs     # 点击→精确字符，27 项 / 136 次
CDP_PORT=9335 BROWSER_CHECK_PORT=1425 node scripts/browser-check/writing-mode-scenes.mjs    # 场景截图，64 项 / 9 篇

# 发版相关
node scripts/generate-latest-json.mjs --tag v0.9.0 --out latest.json   # 生成更新清单（CI 里自动跑）
node scripts/verify-release.mjs 0.9.0                                  # 发版后匿名验收（清单 + 版本 + 安装包 + 验签）
```

## 环境备忘（本机 WSL）

- **`git push` 走 22 端口偶发被掐**：改走 GitHub 的 443 入口即可——
  `GIT_SSH_COMMAND="ssh -p 443 -o StrictHostKeyChecking=accept-new" git push git@ssh.github.com:Z3O1/Typst-pad.git HEAD:main`（先 `ssh -T -p 443 git@ssh.github.com` 验证认证）。
  - **`-o StrictHostKeyChecking=accept-new` 不可省**：沙箱不允许写 `~/.ssh/known_hosts`，缺了会 `Host key verification failed` 而看起来像权限问题。`git fetch origin` 也常失败，要刷 `origin/main` 就显式用 443 的 URL 并指定 tracking ref：`git fetch git@ssh.github.com:Z3O1/Typst-pad.git main:refs/remotes/origin/main`。
- **端口归属**：`1420` = Vite（`tauri dev` / `dev`）；`9333` = 验收用 headless Chrome 的 CDP 端口。两者都可能被上次没退干净的进程占着；查占用：WSL `ss -ltnp | grep :1420`、Windows `/mnt/c/Windows/System32/netstat.exe -ano | findstr :1420`（镜像网络下 Windows 侧监听同样会挡住 WSL 绑定）。
- 无显示器环境：GUI 跑不了桌面端，验收一律用 `scripts/browser-check/`（headless Chrome + CDP）；`gh` 用 Windows 版 `/mnt/c/Program Files/GitHub CLI/gh.exe`（需 `--repo Z3O1/Typst-pad`）。
- **headless Chromium 两种起法**（见「测试」）：Windows Chrome（镜像网络下 WSL 才能直连 localhost:9333）或 **WSL 里 Linux Chromium**（Playwright 缓存里的 `chromium_headless_shell-*`，不依赖 Windows 网络；本机 `chromium-1234/chrome-linux64/chrome` 会 `Trace/breakpoint trap` 崩掉）。**进程要用托管后台任务起**（前台 `nohup … &` 活不过一次工具调用），收尾按自己记的 job/端口关掉。

## CI / 发布约定

- `ci.yml`：`test` job（ubuntu）push main/PR 跑 类型检查 → 单测 → prettier 格式检查 → 前端构建 → rustfmt 检查 → clippy（`--all-targets -- -D warnings`）→ `cargo test`；`build-bundles`（windows）**main push 或 workflow_dispatch 触发**（PR 不构建），Rust 缓存用 `shared-key: tauri-build-windows`（**必须与 `release.yml` 相同**，否则 release job 读不到缓存）。
  - **2026-09-19 补的三门**：此前 `test` job 只跑 `cargo check` —— 61 个 Rust 单测**从来没在 CI 跑过**、`rustfmt` component 装了却从不调用、clippy 从不跑（本地积了 15 条告警）。现在格式/静态检查与单测都成门，**摘一道就等于没有**（红线 12）。
  - `cargo check` 那一步**被 clippy 取代**（不是漏了）：`clippy --all-targets` 覆盖同样的编译面并把告警升级为错误；两步并存只会让同一份代码用两套 driver 各编一遍，白等一次全量编译。
- `release.yml`：`v*` tag 触发，自行 checkout + 构建 + 发草稿 Release（不依赖 ci.yml 的 artifact），吃 main 分支写入的缓存。
- **自动更新与签名密钥**：
  - 私钥/密码存在仓库 Secrets。**本机备份有两份**：仓库内 `.updater-keys/`（已 gitignore，但**在工作区里**——`git clean -xfd` 或误删仓库就一起没了）与 `~/.tauri/`（`typst-pad.key` / `.key.pub` / `password.txt`，0600）。丢了就再也发不出更新；本地打包用 `TAURI_SIGNING_PRIVATE_KEY_PATH=~/.tauri/typst-pad.key`。
  - **pubkey 已写入 `tauri.conf.json` ⇒ 所有 `tauri build` 都必须有私钥**（缺了直接失败），所以两个 workflow 的构建步骤都传了这两个 env。**推论：Secrets 缺失时 main 的 CI 会红**，别当成缓存问题排查；PR 不跑 `build-bundles`，fork PR 也不需要密钥。
  - 构建后由 `generate-latest-json.mjs` 生成 `latest.json`（ci.yml 里只验证"生成得出来"，release.yml 里与安装包一起上传）。脚本坏了要在 main 上就发现。
  - **草稿 Release 客户端拿不到**，所以"发版要 Publish"从"对外可见"升级成"自动更新能不能生效"。
  - **发版后的匿名验收就一条命令**：`node scripts/verify-release.mjs <版本>`（匿名取 `latest.json` → 核对 version → 下载安装包 → 用 `tauri.conf.json` 的 pubkey 验 minisign 签名，四步一次跑完，退出码 0 = 全过）。**别临时手写解析**：2026-09-16 手写那次把 minisign 的 `trusted comment` 签名（纯 64 字节、没有头）当成了主签名，解出乱码 alg、误报"验签失败"；正确做法是**按"哪一行 base64 解出来是 74 字节"挑主签名**（2 字节 alg + 8 字节 keyid + 64 字节签名）。
  - **自动更新失败先查"仓库是不是公开"与"草稿 Publish 了没"，别一上来就判成本机网络过滤**（2026-09-14 判错过一次）：① `gh api repos/Z3O1/Typst-pad --jq .private` 应为 `false`；② `/mnt/c/Windows/System32/curl.exe -sL -o NUL -w '%{http_code}\n' https://github.com/Z3O1/Typst-pad/releases/latest/download/latest.json` 应为 `200`；③ 才轮到网络。updater 是**匿名**请求，私有仓库对匿名一律 404，而插件对非 2xx 只记日志、最后统一报 `Could not fetch a valid release JSON from the remote`。
- **缓存纪律（事故后固化，勿回退）**：
  - rust-cache **禁止加 `cache-on-failure`**：被 cancel 的 run 上传缓存会被截断（实测 588MB 只传了 542MB），后续 run 精确命中同 key 不覆盖 ⇒ 半成品缓存永续，每次构建重编 55 个 crate（13 分钟）。只有成功完成的 run 才允许保存缓存。
  - **"run 运行中不要 push main"已被红线 9 作废**（用户接受 cancel 的缓存代价；仅保留"能一次推完的提交就一次推完"的建议）。
  - 缓存损坏后的修复流程：`gh cache delete <key>` → 用 **workflow_dispatch 手动触发**（不是 push）→ 等 run 自然完成 → 再手动触发一次验证（预期仅 2 个 Compiling、~3 分钟）。
  - `tauri-bundle-tools` 缓存 key 含 `hashFiles('package-lock.json')`；健康缓存命中时构建 ~3 分钟（2 个 Compiling），全量 ~16 分钟（78 个 Compiling）——数字异常即缓存失效信号。
  - rust-cache 的 key 还含「Rust 工具链版本哈希」：`dtolnay/rust-toolchain@stable` 跟到新的稳定版后 key 整片失效、全量重编（一次性重建，不是回归；排查先看 "Cache Rust build" 的 Restore Key 与 "No cache found"）。
- **action 版本约定（Node 24 运行时）**：`actions/checkout@v5`、`actions/setup-node@v5`、`actions/cache@v5`、`actions/upload-artifact@v6`（v5 只是预备支持，必须 v6）、`softprops/action-gh-release@v3`，两个 workflow 保持一致。升级 action **不影响任何缓存 key**。
- **仓库可见性与推送规则**：
  - 仓库已是**公开**（`gh api repos/Z3O1/Typst-pad --jq .private` → `false`）——这是自动更新能工作的前提，**别改回私有**。
  - ruleset「protect main」（id `20191962`）：私有 + 免费账户时不生效；转公开那天被强制生效、直推 main 报 `GH013 … Changes must be made through a pull request`。已按用户选择**改成只保留 `deletion` + `non_fast_forward`**（禁删分支 / 禁 force push，不要求走 PR）⇒ 直推 main 正常。跨域改规则用 `gh api -X PUT repos/Z3O1/Typst-pad/rulesets/<id> --input <完整 JSON>`（PUT 是整体替换）。
  - 万一将来又冒出「必须走 PR」类规则：要么按用户偏好放宽该 ruleset，要么走 `git push HEAD:refs/heads/<分支>` → `gh pr create` → `gh pr merge --squash --delete-branch`。**不要**为了绕开它去 force push 或改 remote。
- **版本升级流程**：**先得到用户明确指令**（红线 11）→ 改版本号（三处一致）→ 合并 main（自动构建）→ 打 tag → **草稿 Release 一建好就直接 Publish，这一步不必再问**（`gh release edit v<版本> --draft=false`）。
  - 需要"等构建完再发"时用**一次性延时动作**（挂成后台 job，有界重试：每 ~30s 查一次，看到草稿且资产齐了就 Publish，上限 ~45 分钟），**不要写轮询循环**（红线 9）。
  - **探"草稿建好了没"必须用 `gh release view <tag> --json isDraft,assets` 或 `gh api 'repos/Z3O1/Typst-pad/releases?per_page=1'`**；`gh api repos/.../releases/tags/<tag>` 对**草稿一律返回 404**，拿它当探针会空转（犯过：90 次循环空转约 40 分钟）。判断条件要写严：只在 `.draft == true` 时才 Publish，取不到值算"还没好"。
  - **发布前确认资产齐了再 Publish**（`latest.json` + `Typst-pad_<版本>_x64-setup.exe` + 它的 `.sig`，缺一个客户端就会下到 404）。
  - **Publish 之后别立刻断言"没生效"**：`releases/latest/download/...` 的重定向走 CDN，实测约 1 分半才切到新 tag。等 1~2 分钟再验。
