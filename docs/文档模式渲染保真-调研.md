## 结论（先看这段）

1. ~~**写作模式现在的渲染是"用 CSS 复刻 typst 的观感"，不是 typst 的排版结果。**~~
   **已改掉**（2026-09-15 阶段 1~3 落地，见第十~十三节；2026-09-18 随 PR #60 合并进 `main`）：
   非光标块显示引擎自己画的那一块切片，断词、字距、`#set`、宏与包全都在切片里；只有光标所在的
   那一块是源码、仍由浏览器折行。下面第一节与第二节记的是**改动之前**的差距，别当成现状。
2. **"和真实 rust typst 一样渲染"只有一条路：显示引擎自己的产物** —— 整篇编译一次，把每个
   源块在页面上的那一块切下来当渲染结果，光标所在的块展开成源码。
   **本仓库的公式 widget（`compile_math` → 内联 SVG）就是这条路的最小版本**，把它从"公式"
   推广到"块"就是全部工作（**已经走完**：见第十~十三节）。
3. **这条路已经被同栈的独立实现走过**（Tauri v2 + CodeMirror 6 + 内嵌 typst 0.15，无 wasm，
   见第六节），它把形态命名为「渲染表面 + 源码透镜」，并留下了"两个各自排版的系统无法共存"
   的实证。代价必须认下来：**正在编辑的块显示源码；渲染块没有文字层（浏览器查找 / 拼写检查 /
   无障碍拿不到）；页级特性（页眉页脚 / 页码 / 分页 / 多栏）降级为源码。**
   （其中"渲染块不可跨块选择/复制"**已经补上**：拖选 + Ctrl+C 走"指针 → 源码位置"，
   见第十二节；文字层仍然没有。）
4. **HTML 导出不是答案**：0.15.1 仍是 feature flag，官方文档写"不要用于生产"；它的输出
   **不带任何源位置**，且**没有分页**（第七节）。
5. **真要动手，先做阶段 0 探针（`geometry_for_range`），不要先动前端。** 唯一的未知是
   "源块 ↔ 版面区域"的切分质量与性能，先量它（第八节）。

## 二、为什么 CSS 这条路永远到不了

- 文字排版是引擎算法的产物（行断点、伸缩、断词、CJK 禁则、`par.justify`），浏览器不会算出
  同一个结果。
- `#set text(size:)` / `#show` 规则 / `#let` 函数 / `@preview` 包是**代码**，CSS 无从执行。
  写作模式面对它们只有两个选择：无视（**块级渲染落地之前就是这么做的**），或者把它当普通文本显示。
- 因此"一样"只能等于**显示引擎的产物**。这也是为什么公式那条路（以及后来"整块切片"那条路）
  才是"真"的。

## 三、可行方案：渲染表面 + 源码透镜（块级切片）

### 3.1 原理

1. 整篇编译一次（本仓库**已经**每次按键全量编译：`+page.svelte:1318` 无防抖 → `:1435 runCompile`），
   页高用 `page(height: auto)`（`compile_math` 已在用），版心宽取编辑器正文列宽（复用 0.7.9 的
   `compile_with_page_width`，`typst_world/compile.rs`）。
2. 在编译产物（页帧）里，把每个**源块**对应的渲染区域算出来（页号 + x/y + 宽高 + 基线）。
3. 编辑器里：**非光标块**用 `Decoration.replace` 换成该区域的 SVG 切片（块级 widget）；
   **光标/选区进入的块**不挂 widget，源码自然露出 —— 与现有公式 widget 完全同一套机制。
4. 点击切片 → 用帧里的字形位置反查源码偏移，把光标落到**正确字符**（不是块首）。

### 3.4 已知代价（必须提前认）

- **正在编辑的那一块必须是源码**。这是 Typora 模型的固有性质（连 Typora 的活动行也是 markdown），
  不是实现缺陷。
- **渲染块是图片**：跨块拖选、复制、查找、拼写检查、无障碍都拿不到。补救是二期加"文字层"
  （按字形位置铺绝对定位的 span，pdf.js 那套思路），能做但属于额外工作。
- **单栏里没有"页"**：`#set page`、页眉页脚、页码、分页、脚注落页底、多栏、`#place` 这些
  按定义与 PDF 不同 → 这些块降级显示源码。
- **暗色**：要么保持白纸（推荐），要么反色（文档自带颜色会失真）。
- **性能**：编译次数不变，新增 N 次小区域 SVG + 每块几何计算；需按视口取块并缓存。

## 四、机制区分：整篇切片 ≠ 片段重编（别被吓退）

外部资料列的"块级重渲染会坏"（计数器、`@ref`、`#outline`、脚注、`context`、`#place`）说的是
**把片段单独拿出来重新编译**的坏法——那种做法下编号、引用、脚注内容全是错的。

**我们的方案是从整篇编译的产物上切片**，所以数字、引用、脚注内容全对；真正的问题只是**几何**：

- 脚注正文落在页底 ⇒ 它的区域与引用它的段落不连续；
- `#place` / `page.background` 的内容不属于任何流式块；
- 内容可能超出"页"的边界（typst 允许画到帧外，0.7.6 的公式下标被裁就是这一类）。

⇒ 因此切分规则应当是**"按流式块在页面上按 y 序切带"**，而不是"按 span 求并集"。
`FrameItem::Tag`（按位置压入页帧，见 3.2 表）给的正是"流式块从哪个 y 开始"，这是切带的天然依据。
这条是阶段 0 要量的核心。

## 五、实现要点与坑（本节是推断 + 源码依据，未实测）

1. **增量编译要先接上**：本仓库现在**每次编译都新建 World + 新建 `Source`**
   （`typst_world/world.rs`，四处 `TypstWorld::new`），comemo 只能命中不依赖 Source 的层。
   官方姿势（`typst-cli watch`）：World 建一次 → 每次只 `world.reset()`（清文件/时间缓存，字体不清）
   → 用 `Source::replace()`（`typst-syntax/src/source.rs:85`，内部 `edit` 做增量重解析）原地更新
   → 编译后 `comemo::evict(10)`。要做"每按键重切块"，这条基本是前提。
2. **`today()` 是 comemo 的失效源**：`TypstWorld::today()`（`typst_world/world.rs`）每次调用重新取
   `SystemTime::now()`，文档一碰 `datetime` 就会全 miss。
3. **comemo 缓存是进程全局的**，而本应用支持 `Ctrl+Shift+N` 多窗口 ⇒ 多窗口必须各用不同
   `FileId`，否则互相命中错结果（未保存文档目前统一 `main.typ`，这条要查）。
4. **坐标系与变换**：`FrameItem::Group` 要反转 `transform`、按 `clip` 剪裁才能映射回本层
   （`jump_from_click_in_frame` 就是这么做的；tinymist 自己抄的那份留着 `// TODO: Handle
   transformation.`，说明这是真坑）。现有 `ink_bounds_of_frame`（`typst_world/math.rs`）**只算纵向、
   不看 span、不处理 clip**，必须扩成二维 + 认 span + 处理 clip。
5. **span 与 Source 必须配对**：`Span` 是编译期那份 `Source` 的编号，文本一改，改动点之后的
   编号会漂 ⇒ **click→source 必须用"编译时的那份 Source"**，不能拿最新文本去解旧帧。
6. **typst-ide 要锁版本**：0.15.1 在 crates.io（Apache-2.0）可直接依赖，但它是 pre-1.0 且与
   typst 同步发版；最成熟的消费者 tinymist **没有用它**，自己抄了一份等价实现。⇒ 用它可以，
   但升级 typst 时要预期签名变化。另：0.15.1 的公开面只有
   `jump_from_click / jump_from_click_in_frame / jump_from_cursor / tooltip / definition /
   autocomplete / analyze_* / matchers`，**没有 `highlight` / `references` / `jump_from_position`**
   （0.12–0.15 都没有）——别按旧教程设计。
7. **别指望给 SVG 打标记**：0.15 还**移除了** SVG 元素上的 `typst-frame` / `typst-doc` /
   `typst-group` / `typst-shape` / `typst-text` 类（0.15 changelog），"按 class 找帧"这条路双重死掉。
8. **切片渲染两种实现各有取舍**：① 每块单独 `svg_in_html`（产物小、IPC 小，但要 N 次渲染）；
   ② 整页渲一次 + 前端按 `viewBox` 包一层（零额外渲染，但每块要复制一份页面 SVG，DOM 体积大；
   同文档 `<use href="#…">` 也可能可行但未验证）。阶段 0 顺带量这个。

**四条结论（都是实测，不是推断）**：

1. **切得出来。** 25 个块里 24 个拿到几何；唯一"没有几何"的正是那两行 `#let` / `#show`
   ——它本来就不渲染。也就是说"没几何的块"恰好等于"该显示源码的块"，判据天然对齐。
2. **能像积木一样按 y 序堆叠。** 4/5 篇 y 单调、相邻块空隙全是正数（+0.43…+11.98pt）：
   块之间不重叠，切出来直接按顺序摞起来就还原整页。
3. **唯一坏掉的是脚注，而且正是调研文档第四节预言的那一类**：`#footnote[...]` 所在段落的
   bbox 被拉到页底（y 76.6→158.9，高 82.3pt），与紧随其后的标题重叠 −54.72pt，该篇正文覆盖率
   掉到 43.6%。⇒ **必须按"流式块在页面上的 y 序切带"，不能按 span 求并集**，这条从推断升级为实测。
4. **切片渲染成本可控。** 第一版把整页项全压进切片时，8 块的切片合计 **100.8ms**（整页才 17.6ms，
   反而贵 6 倍）；改成"只压入与切片矩形相交的项"后降到 5.7~15.1ms，与整页渲一次同量级。
   产物每块 5~20KB（整篇 38~96KB）⇒ **"一块一渲 + 走 IPC"可行**，不必走"整页渲一次 + viewBox 复制"。

**两个只有跑过才知道的坑（已写进代码注释）**：

- **`Font::edges` 的返回值在两条路径上符号约定不同**：正常路径给两个正量（`bbox.y_max`、`-bbox.y_min`），
  而**没有字形包围盒时**（空格等）给的是带符号值（`-ascender`、`|descender|`）。第一版直接按
  `y - up / y + down` 组装，空格字形就产出了**上下颠倒的矩形**（块高为负、行序判断全乱）。
  统一规范化成"两个正值"后才正常。
- **行内构造不是块**：`$a^2+b^2=c^2$` 与 `` `行内代码` `` 起初被当成独立块，把段落切成三段
  （块级 widget 会截断段落）。现在 `Raw` / `Equation` / `Code` 只在**独占整行**时才算块。

**未覆盖的字符**是标记语法本身（`=`、`$`、`^`、反引号）与代码行 —— 它们不产生字形，属预期，
也正好对应"源码透镜"里保持源码显示的那些块。

- 滚动到没渲过的区域 → 先是源码，`onBlocksNeeded` 去抖 150ms 后按新窗口重编译一次；
- 被切片盖住的公式**不再请求编译**（每个公式都是一次 IPC 往返，实测能耗掉几十次）。

**① 切片几何等价验收（真实产物，不是桩）**：`npm run fixtures:blocks`（Rust `dump_block_fixtures`）
导出每块的真实区间/几何/SVG 到 `.browser-check/block-fixtures.json` → 浏览器注入 →

| --- | --- | --- | --- | --- |
| 段落与标题 | 3 | 最大偏差 **0.01px** | **0.00px** | 157.7px = 157.7px |
| 列表 | 5 | 最大偏差 **0.01px** | **0.00px** | 217.8px = 217.8px |
| 公式与代码 | 4 | 最大偏差 **0.01px** | **0.00px** | 209.4px = 209.4px |

**①b 场景验收（`writing-mode-scenes.mjs`，40 项）**：按**文档形态**逐场景过一遍真实产物 ——
标题层级 / 中文长段落 / 列表与嵌套 / 公式 / 代码与表格脚注 / 文档级 `#set` 对照 ——
每场景断言切片数、宽度、逐块高度、相邻缝，并留一张截图（`.browser-check/scene-*.png`）。
最后一个场景还走一遍"编辑 → 重编译 → 切片仍在 → `Ctrl+E` 往返（0.8.2 起模式切换是 Ctrl+E，Ctrl+/ 归注释）"。

**①c 场景验收抓到的真 bug（已修）**：脚注场景一开始是**代码块与表格各渲染两遍 + 76px 空隙**。
根因：typst 允许把内容排到远处（脚注正文在页底），而块的墨迹包围盒是**并集** —— 带脚注的段落
因此得到一个一直伸到页底的高盒子（88pt），把后面几块的中点切带压扁：代码块被压到 ≤0.5pt
（切片被丢弃 → 回退成源码/旧代码块 widget），而它的内容又被那张超长切片又画了一遍。
修法：**块自己的纵向区间夹紧到它在 y 序里下一个块的顶**（`compile_blocks` 的 2b 步），
带高退化时留最小带而不是丢块。修后各带首尾精确相接（73.4+25.1=98.5≈98.6），截图里重复消失。
**残留限制**：脚注正文（页底装饰）在写作模式里不再显示 —— 这比"显示在别人的切片里"好，但仍是限制。

**② 窗口化回归网**（`windowing_keeps_payload_bounded`，常驻测试）：断言"窗口内的块数与产物
字节数远小于全渲"（实测窗口内 19 块 / 1179KB vs 全渲 161 块 / 10019KB），并在窗口化后
**不丢失任何块的几何**（前端靠 `found` 判断"这块能渲染只是还没渲"）。

**③ 开销实测（决定了当前架构的取舍，别只看一半就改）**：

| 文档 | 逐块切片·全渲 | 逐块切片·窗口化（±4000 字符） | **整页 SVG（一次）** |
| --- | --- | --- | --- |
| 2 027 字符 | 1 169KB | 574KB | **216KB** |
| 6 147 字符 | 3 488KB | 1 158KB | **527KB** |
| 12 407 字符 | 6 976KB | 1 153KB | **1 006KB** |
| 20 967 字符 | 11 730KB | 1 172KB | **1 675KB** |

结论：**逐块 SVG 会各自复制一份字形轮廓 ≈ 58 字节/源字符**，整页 SVG 只有它的 1/7；
窗口化后与整页同量级（1.2MB vs 1.7MB）且**不必再传一次整页**。所以当前"窗口化逐块切片"
不是最优保真方案里最省的一条路（更省的是"整页渲一次 + 前端按 viewBox 切"，但要在前端做
`<use>` 共享与 id 命名空间，且每个切片会克隆整页内容），**但它是量级可控、且已经过真机
浏览器验收的一条**。真要再优化，先看这张表再动手。

**它抓到的 bug（已修）**：`== 5` 那一段的 5 个公式在编辑器里**挤成一团**。
定位：把 y 480..540 的帧项倒出来看，**5 个公式的字形项全在同一个 y 带（499.2–502.5）里交错** ——
也就是 typst 自己把它们排成了一行。原因是这份源码里 `$0=emptyset$` **定界符内侧没有空白**，
按 typst 语义是**行内公式**（`$ x $` 才是行间），所以它们属于同一个段落、被连排；而我们的分块
规则当时按"独占整行"把它们切成了 5 块 → 5 条带互相重叠、DOM 顺序与页面顺序对不上。
**判据改成跟 typst 语义走**：`Equation` 只有在**定界符内侧两侧都有空白**时才自成一块，
`Raw` 只有 ```` ``` ```` 围栏才自成一块（`$x$` 哪怕独占整行也留在段落里）。
修后这一段是**一块**（y=496.3 h=36.9），截图与真实排版一致。回归测试：
`block_partition_matches_typst_semantics`。

**给文档作者的提示**（不是 bug）：想在写作模式里看到"独立成行的公式"，源码要写
`$ 0 = emptyset $`（定界符内侧留空格），而不是 `$0=emptyset$` —— 后者在任何 typst 前端
（预览、PDF）里也都是行内公式、会被连排。

### 真实文档体检（第二轮）：光标竖直移动跳回开头（2026-09-15，用户反馈）

**现象**：在 `== 6` 前面（也就是最后一块里）按 ↑，光标**跳回文档开头**（截图与 DOM 都复现过）。

**根因（读 CodeMirror 源码定位）**：竖直移动 `moveVertically` 是从光标位置逐像素往上/下扫，
扫到**文本行**才停 —— 而 `posAtCoords` 对非文本块（widget）的处理是
`yOffset = block.top - halfLine; continue`，**直接跳过**。写作模式的切片全是 widget，
于是"往上"时它一路跳过所有切片、扫到内容顶部，`yOffset < 0` 时返回
`PosAssoc(0, 1)` —— **位置 0 = 文档开头**。所以这不是"偶然跳错"，而是必然。

**修法**：不跟 CM 的扫描较劲（改不了），而是在写作模式下自己接管竖直移动：
`live-preview.ts` 挂 `Prec.high` 的 ArrowUp/ArrowDown（连带 PageUp/PageDown，它们走同一条
`moveVertically`），先让 CM 算一次默认结果 ——

* 默认结果**仍落在当前格内** ⇒ 交回默认（块内逐行、保留目标列）；
* 一旦会跨格 ⇒ 把光标放到相邻格边界：向上 = 上一格源码末尾（`coverTo - 1`）、
  向下 = 下一格源码开头（`coverFrom`）。

判定抽成纯函数 `block-plan.verticalBlockTarget`（可单测）。实测（`writing-blocks.mjs` 第 8 组）：
从末尾连按 ↑ 的展开序列 = 最后一段 → 列表项 → 第一段 → 标题 →（停在标题，不再乱跳）；
从开头连按 ↓ 单调前进、最终走到最后一块。
阶段 2 把这个判定的参照从"格子"收到了"块正文"（见第十一节），段段之间不再多停一拍。

> **2026-09-16 更新（用户：「我希望光标移动和代码模式的光标移动一样」）**：上面这套"一次跨一整块"
> 已经**作废**。现在的规则是：默认走法（`moveVertically`）**没跨过未展开的切片**就完全交回
> CodeMirror（逐可见行、空行也停、保留目标列）；跨过了才按**源码行**走一行（判定 =
> `crossesCollapsedCover` + `sourceVerticalTarget`，落点的列先用字符列估、再用 `measureColumn`
> 按真实几何校正）。"段段之间不再停一拍"那条**反过来**了 —— 现在空行也停一拍（代码模式如此）。
> 详见 `CLAUDE.md` 的「竖直移动 = 代码模式的语义」与 `docs/写作模式块级渲染-现状与交接.md`。

### 四条实测结论

1. **点击精度：125/125 全中。** `writing-blocks-hit.mjs` 拿 8 篇真实产物里的 **495 个探针点**
   （每块横向 5 × 纵向 3 的网格，期望值由 Rust 侧真实几何算出）在浏览器里逐个点下去，
   光标落到的字节偏移与夹具记的**逐一相等**（含中文 3 字节 / emoji 4 字节的换算）。
   验收按块轮转下单（点完一块它就变源码，下一次点另一块），默认每块取 4 个点、`HIT_FULL=1` 跑全网格。
2. **滚动锚定不能自己写 `scrollTop`。** 第一版在点击后自己算 `scrollTop += (实测 - 目标)`：
   实测 91px 偏差 —— CodeMirror 的 measure 循环里**自己也有锚定**（anchor diff），它在我们写完之后
   又改了一次（我们设 1771，它拉回 1680），两次修正叠加。改成把它自己的
   `scrollIntoView(pos, { y: "start", yMargin })` 放进**同一个事务**后，偏差降到 **4px**（行高 30px）。
   翻页同理：光标停在原屏幕高度的偏差从"整屏"降到 **2px**。
3. **"滚动到没渲过的区域补渲"从来没生效过**（阶段 1 的 bug，本次由新验收抓出来）：
   `notifyBlocksNeeded` 用 `buildBlockCovers` 的结果判"有没有块缺切片"，而那条路会把缺切片的块
   标成 `revealed`，判据 `!cover.revealed` 于是永远为假 —— 滚动过去只会看到源码，要等用户敲一个字
   才补渲。改成直接看块表（`found && svg === ""`），并加了"同一个窗口不重复编译"的防抖。
4. **编译失败不必整篇退回源码。** 前后缀差分（`changedSpan`）能判定"哪些块完全没被碰到"：
   改动段之前的块原样保留、之后的块整体平移、相交的块退回源码（区间放宽到并集，只多显示源码）。
   验收第 11 组：插入 `@err` → 其它块的切片还在 + 出错块可见 + 状态栏报错 + 波浪线出现；
   改好后那一块重新变回切片。

### 阶段 2 收尾：编辑期间块表必须"跟着走"（用户报「在一块内 Enter 插入块的时候会有问题」）

**症状**：在块内按 Enter 插入新块之后，正文里有的一整段会**凭空消失**（被一张内容对不上的旧切片
盖住），或者同一段文字**重复显示**（既在旧切片里、又露出一截源码）。

**根因**：块表与切片是上一次编译的产物（旧文档坐标），而格子的边界是按"块的最后一行之后"算的
—— 插入换行改变了行结构，旧坐标放在新文档上会落到错误的行。此前只有在**编译失败**时才用前后缀
差分平移一次，编辑期间原样沿用（"偏一两个字符无害"这个假设对**换行**不成立）。
真机编译有几十到几百毫秒延迟，这段窗口肉眼可见；编译失败时更是不会自愈。

**修法**（都在前端，不动 Rust）：

| 改动 | 位置 |
| --- | --- |
| **每次编辑**都跑一次 `remapBlocksThroughEdit`（前后缀差分 → 没被碰到的块原样/平移、被碰到的退回源码），跑完 `blocksVersion++` 重建装饰 | `+page.svelte` 的 `remapBlocksForEdit`（由 `handleDocChange` 调用） |
| 改动落在**块与块之间**（空行上打字、段落之间插字、文末追加）时，归给"格子里放着它的那一块"（后一块；没有就是最后一块）→ 它退回源码 | `block-plan.remapBlocksThroughEdit` |
| `planBlockCovers` 容忍**越界**（表比文档旧是必然的中间态）：过滤掉落在文档之外的块，**绝不抛异常** | `block-plan.planBlockCovers` |
| `collectRequests` 整体 try/catch（它跑在 ViewPlugin 里，抛出会被 CM 记成 "CodeMirror plugin crashed"） | `live-preview.ts` |

**验收**（都验过"去掉修复就会红"）：

0. **各种输入**（用户后续要求「加入各种输入的测试」）：把 12 个常见编辑动作（段中打字 / 段尾回车 /
   段首回车 / 段中拆行 / 连按两次回车 / 退格合并两段 / 删掉一整段 / 打字后 Ctrl+Z / 粘贴多段 /
   Tab 缩进 / 输入 `$` 起行间公式 / 全选重打）逐个在浏览器里走一遍，每个动作之后都查
   「刚打的标记词看得见 + 一行都没丢 + 不重复 + 切片还在 + 控制台干净」（`writing-blocks.mjs` 第 13 组）；
   外加纯逻辑的**编辑矩阵** `block-plan-edits.test.ts`（4 篇文档 × 每个位置 × 17 种动作 × 四条不变量）。
   **没有修复时这组有 9/12 会红**（`第二段。` 整行被旧切片吞掉）—— 也就是说用户报的 Enter 只是
   这一类问题的一个入口，打字 / 删除 / 撤销 / 粘贴都会撞上。
1. `writing-blocks.mjs` 第 12 组（新增，`&blockslow=1` 给假编译加 350ms 延迟来模拟真机窗口）：
   在文档开头插入新块 → **正文一行都不许丢**（每行要么在源码里、要么在渲染了它的切片里）、
   不许重复显示、控制台不许出现 `RangeError / 装饰重建失败 / CodeMirror plugin crashed`；
   再补一条"文档大幅缩短（全选重打）"——旧坐标越界曾经在这里抛
   `Invalid position 116 in document of length 17`。
2. `block-plan.test.ts` 的"编辑后的增量平移"用例：对 4 篇真实形状的文档 × 每个位置 ×
   （换行 / 空行 / 普通字符）枚举，断言三条不变量 —— 改动必须落在**已展开**的格子里、
   格子边界必须落在行首、未展开的格子必须把那一块正文**完整**盖住（半盖 = 重复显示）。

主题：**"能选、能用图片本身交互"** —— 从切片上拖选出一段（含跨块）并 Ctrl+C 复制，`#link` 能点。

### 一个关键取舍：**没有做"每字形 span 的文字层"**

计划里写的是"文字层（pdf.js 那套：按字形位置铺绝对定位的 span）"。实际落地的不是它，理由两条：

1. **代价与收益不成比例**：窗口内 8000 字符 ≈ 8000 个 span（而那一块本来就已经是一张图），
   且要在 CodeMirror 的内容元素里造出**第二套选区** —— 复制走浏览器、剪切/改写走 CM，
   两套会打架。用"把指针位置翻译成源码位置、再由 CM 落选区"达到的是**同一个用户结果**
   （拖选 → 高亮 → Ctrl+C），选区只有一套，方向键/输入替换/Shift+扩展全都照旧。
2. **复制出来的是源码而不是排版后的文字** —— 这一条与 Typora 一致（Typora 复制出来也是
   markdown 源码），所以不算损失。

仍然拿不到的（要真正的文字层才能有）：**浏览器 Ctrl+F 查找、拼写检查、无障碍**。
换句话说：图片的表面 + 源码的交互，代价是"查不到、读屏读不到"。

### 两条实测踩出来的坑（都已写进 CLAUDE.md）

1. **拖动期间一旦真的落选区，版式会跟着变，位置就"倒着走"**：拖过第 3 段时位置从 19 退回 15 ——
   因为选区把那一段展开成源码、行高变了，指针从"正文行"落到了刚露出来的空行上。修法是拖动期间
   **不落选区**（只更新内部落点 + 画色块），松手才落。顺带：单击时**松手不要再解析一遍**
   （按下的解析已经把光标放好，松手时版式已变 → 实测从"位置 10"被改写成"位置 51"）。
2. **`EditorSelection.range()` 返回的是 `SelectionRange`，不是 `EditorSelection`**：CM 的
   `MouseSelectionStyle.get()` 必须交有 `.ranges`/`.main` 的后者，交了前者 CM 内部读
   `undefined.length` 直接抛，拖选**无声失效**（`dispatch({selection})` 两种都收，所以只有这里会踩）。

### 核对下来的两件事（不用做）

- **"列表项级细粒度"阶段 1 就已满足**：实测夹具里 `- 第一项` / `- 第二项（含嵌套）` / `+ 有序一`
  各自成块（`ListItem` / `EnumItem` 都是块类型，嵌套列表留在父项那一块里）。
- **表格保持整块**：按行切会把表格线与单元格切碎，视觉上更差；而点击定位本来就精确到字符，
  所以"表格里点哪一行"这件事不需要靠切块解决。

## 十三、阶段 3 之二的"手感"两件事（2026-09-15，用户反馈）

### 1) 输入手感：打字期间不再编译（用户报「输入手感很差」→「我说是公式」）

**量出来的问题**（headless Chromium + 桩，页面侧统计 invoke 次数与帧间隔）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 在公式里连打 12 个字符 | **12 次 `compile_blocks` + 12 次 `compile_math`**（其中 12 次 `compile_math` 完全是浪费：光标在公式里时它是源码形态，渲染了也不显示） | **各 1 次** |
| 打字期间的主线程帧间隔 | ——（小文档看不出，长文档靠它兜底） | 最大 26ms / 平均 17ms，无 >50ms 掉帧 |
| 停手后版面对齐 | 慢编译桩 338ms | 慢编译桩 622ms（**故意**的：150ms 去抖 + 公式优先；换来的是一次编译而不是十二次） |

**改法**（三处，都在前端）：

1. **写作模式编译去抖 150ms**（源代码模式仍立即编译）—— 打字时编辑的那一块本来就是源码，
   其它块的切片内容也没变，编译纯属浪费；
2. **有公式要渲时把挂着的块编译再往后推**（240ms）—— 三个编译命令共用一把互斥锁，
   几毫秒的公式不该排在几十~几百毫秒的整篇编译后面；
3. **光标所在的公式不请求渲染**（`selectionTouchesRange` 跳过）—— 直接砍掉一半的 IPC。

### 2) 选中整块不展开（用户要求「选中整个代码块不要展开」）

规则：选区**完整盖住**某一块时，它**不展开**，改用一层淡色底（`.cm-block-crop-selected`）
表示"被选中"；只盖住一部分才展开（那样选中高亮才精确）；选区内容照旧是源码，Ctrl+C 照常。

**两条硬约束（实测踩过）**：

- **光标（选区 head）所在的那一块必须展开**：整块不展开时那一格是图片，图片里没有真实文本，
  浏览器把输入事件发给 DOM 而 CodeMirror 收不到 —— **Ctrl+A 全选之后打字一个字都进不去**。
  所以"整块选中不展开"只适用于光标不在里面的块。
- 于是"**在代码块里**拖选整块"（光标必然在里面）仍然要展开，那就**把两行围栏藏起来**
  （`buildFenceHidingDecorations`：整行替换、含行尾换行），于是看到的就是代码正文 + 精确高亮，
  而不是 markdown 源码。

### 3) 选中整个公式也不展开（用户要求「选中整个公式请写不展开」）

与块级同一套规则（`math-ranges.mathRevealDecision` + `selectionCoversRange`）：选区**完整盖住**
公式时不展开，保持渲染、挂一层淡色底（`.cm-math-selected`）；只盖住一部分、或光标在公式里时
照旧展开源码。判定是纯函数，`live-preview.test.ts` 有 DOM 级用例。

**行内公式（`$x^2$`）直接成立**，实测（headless Chromium + 桩，真实鼠标拖选与真实输入）：

| 手势 | 结果 |
| --- | --- |
| 段落里从公式左边拖到右边 | 选区 `" $x^2$ "` 完整盖住 → 切片留下、挂淡色底、**打字 `z` → 文档变成 `前文z后文`** |
| 整行只有一个行内公式 + Ctrl+A | 保持渲染 → 打字 `z` → 文档变成 `z`（输入没被吞） |

**行间公式（`$ x^2 $` 独占一行）当时不行，根因是它原来的形态**：整行被 `block: true` 的
replace 换成 widget，而那个 widget 是 **`contenteditable=false` 的顶层 `div`**（不在 `.cm-line` 里）。
实测选中它再打字：**文档纹丝不动、字符被插到了下一行**（`$ x^2 $\n后文` → `$ x^2 $\nz后文`），
因为 DOM 里那个位置没有可编辑的行容器，CodeMirror 读到的是"下一行变了"。
（块级渲染那次是同一族的极端版：整个文档就是一张图片 → 输入完全进不去。）

所以把**单行**行间公式改成"**行内 replace（盖整行、含前后空白）+ widget 落在行内 + 行级居中**"
（`MathBlockWidget` 的 `inline` 形态：元素用 `span`、类名 `cm-math-block-inline`，
配套 `Decoration.line({ class: "cm-math-line" })` 给所在行 `text-align: center`）。改完实测：

| 手势（单行 `$ x^2 $`） | 改前 | 改后 |
| --- | --- | --- |
| Shift+End 选中整行公式 → 打字 `z` | widget 留下、**字符插到下一行**、文档没变 | widget 留下 + 淡色底、文档变成 `z\n后文\n` ✓ |
| 程序化选中 0..7 / 0..8（含换行）→ 打字 | 同上（插到下一行） | 分别是 `z\n后文\n` / `z后文\n` ✓ |

**判据必须是"装饰实际盖住的区间"，不是只看公式本身**（`decorated = block ?? 公式区间`）：
单行行间公式连行首行尾空白一起盖（`  $ x $  ` 这样才真的居中），若只按公式范围判"完整盖住"，
就会出现"选区盖住公式、widget 只被盖住一部分"——DOM 里 widget 是**原子节点**，浏览器只能在
它的边缘插入，实测结果是**字符被插到行尾**：`  $ x^2 $  ` 里选中 `$ x^2 $` 打字 →
`  $ x^2 $  z`（而且那一帧 widget 还消失了）。改成按装饰区间判之后，这种"半盖住"照旧展开源码，
打字得到正确的 `  z  `。`buildMathDecorations` 与 `collectRequestsInner` 两处判据同源。

**跨行的行间公式仍是 `block: true` 整行替换**（CodeMirror 不允许 inline 装饰跨行），
那种形态**不适用**这条规则 —— `mathRevealDecision` 的 `inlinePresentation: false` 让它照旧展开，
理由与上面的实测一致：宁可展开，也不能让输入落到别处。

### 4) 标题字号梯度改成跟 typst 一致（用户问「为什么在标题所在块，标题就会变的很大」）

原因不是新 bug，是**第一节那张对照表里的"标题 1.8 / 1.5 / 1.25 / 1.08em"在块级渲染落地后露馅了**：
切片是引擎画的（`heading.rs` 的 ShowSet：level 1 = **1.4em**、level 2 = **1.2em**、level 3 及以下 = **1.0em**，
只加粗不再变大），而光标一进标题块，那一块就展开成源码、由我们的 CSS 画 —— 两套梯度差了 25%~36%，
再加上编辑区正文（16px）本来就比 typst 默认正文字号（11pt = 14.67px）大 9%，叠起来就是"标题突然变得很大"。

| 级别 | 切片里（typst，默认 11pt） | 改前（编辑区 16px） | 偏差 | 改后 | 偏差 |
| --- | --- | --- | --- | --- | --- |
| h1 | 1.4em → **20.5px** | 1.8em → 28.8px | **+40%** | 1.4em → 22.4px | +9% |
| h2 | 1.2em → **17.6px** | 1.5em → 24.0px | **+36%** | 1.2em → 19.2px | +9% |
| h3 | 1.0em → **14.7px** | 1.25em → 20.0px | **+36%** | 1.0em → 16.0px | +9% |
| h4~h6 | 1.0em → 14.7px | 1.08em → 17.3px | +18% | 1.0em → 16.0px | +9% |

改的是 `Editor.svelte` 写作模式的 `.cm-markup-heading-*`（`live-preview.ts` 主题里同名的那几条也一并对齐，
它们只在不带 `.editor-host.write` 的场合生效）。**`line-height` 当时保持原值（1.45 / 1.5 / 1.55）** ——
那只是这一步的中间态：**2026-09-16 起写作模式的标题行高也改成 typst 的 leading `1.65`**（与正文同一个
leading，见第十三节之 7 的第 3 条；现在 `.cm-editor` 里四条 `.cm-markup-heading-*` 都是 `line-height: 1.65`，
只有 `live-preview.ts` 主题里那几条仍是旧值）。下面这组算术是"当时那组行高正好接近标题行盒"的记录，
别再照它改回去：h1 32.5px vs 33.9px、h2 28.8px vs 29.0px、h3 24.8px vs 24.2px。

**剩下的 +9% 是"编辑区正文 16px vs typst 默认 11pt"**，与块类型无关（普通段落也一样）——
要彻底消掉得让源码透镜跟随**文档实际正文字号**（Rust 侧回报、前端当基准），那是另一件事，见第十四节。

验收锁在 `writing-mode-scenes.mjs` 的「标题字号梯度对齐 typst」：h1/h3 = 1.400、h2/h3 = 1.200
（比例与基准无关，正好卡住那条回归），以及各级与切片字号之比 ≤ 1.15；另加 `wysiwyg.mjs` 两条
（标题 = 正文 × 1.4；Ctrl+1 后 = 22.4px）。

### 5) 没有输出的块整格隐藏（用户问「为什么 `#` 的代码还是会显示出来」）

`#set` / `#show` / `#let` / 纯注释行这类**规则**在真排版里没有输出 —— 用用户真实文档跑一遍引擎侧探针
（`.browser-check/real-scene.typ` → `cargo test dump_real_doc_fixture -- --ignored --nocapture`）看得最清楚：

```
REALDOC-BLOCK: Paragraph  [   0,  50) y=   0.0 h=   0.0 found=false svg=0KB   ← #show math.equation: set text(...)
REALDOC-BLOCK: Heading    [  51,  55) y=  58.5 h=  11.3 found=true  svg=1KB
```

首行那块 `found=false`、高度 `0.0pt`、一个字形都没有 —— "渲染表面"是"按 y 序把引擎画出来的东西
切成一块一张图"，没有画面就没有图可切，于是它一直退回源码显示（合文档第一节那句"不是 bug、是没设计过"）。

**现在：整格隐藏**（用户 2026-09-16 选定「完全隐藏，和 PDF 一样什么都看不到」）。
`buildHiddenBlockDecorations` 用整行的 `Decoration.replace({ block: true })`（**不带 widget**）把格子的
源码藏掉、高度归零（连块尾空行一起藏，否则凭空多一行空行）；光标/选区进去时照旧展开成源码，可编辑。

**最容易写错的一处**：`Block.noOutput`（"引擎说这块没输出"）与 `found: false` **不是一回事** ——
后者还有"块表过期 / 编译失败"那一族（`remapBlocksThroughEdit` 会把块标成 `found:false`），
那种块**必须永远展开**（否则用户刚打的字会凭空消失）。所以 `noOutput` 只在"这一次成功编译、
引擎确实什么都没给这一块"时为 true，remap 里要显式清成 false。

验收：`writing-mode-scenes.mjs` 的「没有输出的块（#set / #show）」四条（隐藏 / 其余照常渲染 /
光标进去展开 / 离开又藏起来）、`block-plan.test.ts` 两条、`live-preview.test.ts` 两条（含"过期块绝不隐藏"）。

### 6) 块与块之间的空行归「上一块」（用户报「用 enter 拆分块的时候，光标会有问题」）

现象：在行尾按 Enter 拆分块之后，**光标被画到正文列的最右边**（截图里就是那一根飘在右边缘的竖线）。
复现与根因（headless Chromium + 用户真实文档的夹具）：

| 状态 | `coordsAtPos(head).left` | `domAtPos(head)` | 光标所在行 |
| --- | --- | --- | --- |
| 修前 | **1087**（= 正文列右缘） | `.cm-content`（**没有行 DOM**） | 新空行（行首 = 上一块切片的结尾） |
| 修后 | **304**（= 行首） | `.cm-line` | 同上 |

在行尾按 Enter 后光标落在**新空行的行首**，而那个位置同时是**上一块切片（`Decoration.replace({block:true})`）
的结尾** —— CM 对"块 widget 结尾那个位置"的定位会落到 widget 自己身上（`coordsAtPos` 给出 widget
的右下角），若那一行又是空行、CM 干脆没给它建 DOM，`domAtPos` 就退化成 `.cm-content`。

修法：**让块与块之间的空行归「上一块」的格子**（`planBlockCovers` 里每格 =「自己的第一行行首 →
下一块的第一行行首」）。这样按 Enter 之后光标落在**上一格的内部**（不是边界）→ 那一格照常展开源码
→ 位置有真实 DOM → 光标画在行首。**引用计数式的连带修改**（三处，漏一处就白改）：
`remapBlocksThroughEdit` 的"空行上打字"落点改成"末尾在改动点之前的最后一块"、
以及"接管结果与默认一致时返回 null"。（当初还有第三处 `verticalBlockTarget` 向上取
`covers[next].block.to`，但那个函数 2026-09-16 已随"竖直移动照代码模式走"一起删掉了 ——
**"空行归上一格"这条约束本身仍然有效**：光标落在空行上时，它必须在**上一格的内部**，
不能落在 widget 的边界上。）渲染出来的页面不变（无论空行归哪一格，它都被某张切片吃掉、不占高度）。

验收：`writing-blocks.mjs` **第 16 组**三条 —— **把修复回退掉实测会红**（`x=1087` / `domAtPos` 不是行），
另加 `block-plan.test.ts` 里跟着改语义的 6 条断言。

### 7) 源码透镜跟随文档字号与行距（用户：「不要光标在哪里哪里就变大了」）

现象：光标一进某一块，那一块的字与行距就跟切片对不上（旧值：编辑区固定 16px / 行高 1.9，
而切片是 typst 默认 11pt = 14.67px / 行高 1.65 → **字大 9%、行盒高 26%**）。

改法（**渲染表面仍然完全按引擎，改的是源码透镜**）：

1. **Rust 侧回报文档正文实际字号**：`block_geometry::document_text_pt` —— 帧里所有文本按**字符数**
   投票取众数（正文占绝对多数，标题/代码块只是少数），随 `compile_blocks` 的 `textPt` 返回。
   实测：默认文档 11pt、`#set text(size: 12pt)` 的文档 12pt、空文档回落 11pt（`document_text_size_follows_the_document`）。
2. **前端把它挂成 CSS 变量**：`--write-doc-px = textPt × 4/3`，写作模式的 `.cm-editor` 字号取它，
   `.cm-content` 的行高取 typst 的 `par.leading`（0.65em → **1.65**）。缺省 14.6667px（老后端/桩也对得上）。
3. **标题**：梯度仍是 typst 的 1.4 / 1.2 / 1.0em（第十三节之 4），行高改成 1.65（标题也用同一个 leading）；
   **标题行的上下 padding 删掉**（实测取舍，见下）。

实测（600px 视口 + 真实夹具，比例 1.32 ≈ 真实应用的 1.333）：**光标进出块时页面高度差** ——

| 场景 | 改前（16px / 1.9 + 旧 padding） | 现在 |
| --- | --- | --- |
| 中文长段落 | +22px | **0px** |
| 标题层级 | +19px（padding 用 typst 的 1.8em 时是 **+40px**） | **+3px** |
| 代码与表格 | +45px | **+8px** |

标题 padding 的三种取值都量过：`0` → +3px、旧的 `0.6em/0.2em` → +19px、typst 的 `1.8em/0.75em` → +40px。
**结论是"不加"**：切片是"按 y 序把页面切成的带"，标题周围的空白**已经分散在相邻块的带里**
（带在相邻墨迹的中点处切），源码形态再补一份就翻倍了。

验收：`writing-mode-scenes.mjs` 的「光标进出块时页面不许变高」（两条高度差 ≤12px + 两条字号：
默认文档 14.6667px、`#set text(size: 12pt)` 的文档 16px）、以及那一组里"与切片字号之比 1.0 ± 0.02"
（从原来的 1.0~1.15 收紧）。`writing-blocks.mjs` 场景 B 的拖选改成"先点进代码块、再对着**展开后的
真实源码**拖整块"—— 夹具在 1400px 视口下被放大 2.1 倍，"切片比展开后的源码还高"，指针会落到下一段上；
真实应用是 1.333，没有这个错位（高度等价已在 600px 视口下量过）。

## 十四、其余未验证 / 未决（别当结论用）

- **Release 构建下的耗时未测**（阶段 0 的数字全部来自 debug 构建）；跨按键增量（World 复用 +
  `Source::replace`）的实测加速比同样未测。
- **脚注正文（页底装饰）在写作模式里不显示**：夹紧之后它落在任何块的带之外（实测如此）。
  要显示它得单独切一块"页底装饰"并贴在页面末尾，属阶段 3 的事。
- **浮动/`#place` 的内容**同理（块区间外的排版内容目前不会被任何切片覆盖）。
- ~~源码透镜的正文字号不跟随文档~~：**已做**（2026-09-16，见第十三节之 7）——Rust 侧
  `document_text_pt` 回报文档正文实际字号，前端 `--write-doc-px` 用它，行高取 typst 的 leading。
- **段落间距（`par.spacing` 1.2em）没有在源码形态里体现**：源码里的段间空白就是用户自己写的那条空行
  （1.65em），而渲染里是 1.2em ⇒ 两个都展开时会有约 0.45em 的差。单块展开（常态）量不出差别
  （空行归上一块的格子、由切片吃掉），所以先留着。
- **表格 / 代码块这类"源码比渲染长"的块**：展开时光标那一块必然变高（比如表格源码 5 行 vs 渲染 2 行），
  这是"源码透镜"的固有代价（Typora 也一样），当前实测 代码与表格 场景 +8px（行数相同的代码块几乎不差）。
- **块粒度**：嵌套列表项目前整个 `ListItem` 算一块（外层），是否要细到每一项未定。
- ~~诊断波浪线在切片上的落点~~、~~"点击切片 → 光标落在正确字符"的精度~~：
  阶段 2 已落地（见第十一节：错误所在块强制退回源码 + 帧遍历的命中测试，两者都有真实几何验收）。
- `typst-ide = "0.15.1"` 加进本工程能否直接编译（依赖树里 `typst-html` / `indexmap` / `unscanny` /
  `serde` 都在，但版本对齐未实测）。
- `svg_in_html` 的 `Tracked<LateLinkResolver>` 具体写法未编译验证。
- "改 `viewBox` 做局部裁剪"在含 `clip-path` / 渐变 / `render_bleed` 的页面上是否 100% 安全未实测。
- comemo 增量（World 复用 + `Source::replace`）的实测加速比未知。
- 块切分的**粒度**取舍（整列表 vs 单列表项 vs 整表）对手感的影响未知。
- `TextItem::bbox()` 的 y 轴方向（源码注释说是 y-up 转 frame 方向有符号翻转）需实测确认。
